TLSNotary Proof Schema v1

Canonical schema URL: https://anchr-spec.org/spec/proof/tlsn/v1

This schema identifies a TLSNotary proof for an HTTPS response and the predicate that an Anchr Oracle evaluates before releasing settlement material.

Predicate Shape

The predicate describes the HTTPS target and deterministic response conditions. Implementations may add schema-specific fields, but the following fields are the stable v1 shape: 

{
  "target_url": "https://api.example.com/resource",
  "domain_hint": "api.example.com",
  "conditions": [
    {
      "type": "contains | regex | jsonpath",
      "expression": "$.status",
      "expected": "COMPLETED",
      "description": "response status is completed"
    }
  ],
  "max_attestation_age_seconds": 300
}
Field Meaning
target_url HTTPS URL that the TLSNotary presentation must bind to.
domain_hint Expected TLS server name. It must match the target URL host.
conditions Deterministic predicates over the revealed response body.
max_attestation_age_seconds Maximum accepted age for the TLSNotary presentation.

Proof Payload Shape

The proof payload contains a TLSNotary presentation or an encrypted attachment reference to one. The presentation must reveal only the headers and body fields needed for condition evaluation. 

{
  "presentation": "<bytes or attachment reference>",
  "revealed_headers": { "content-type": "application/json" },
  "revealed_body": "{...}",
  "session_timestamp": 1770000000
}

Response Data Shape

On success, verifiers expose the server identity and revealed response data used for the verdict: 

{
  "server_name": "api.example.com",
  "revealed_headers": { "content-type": "application/json" },
  "revealed_body": "{...}",
  "session_timestamp": 1770000000
}

Verification Requirements

  • Verify the TLSNotary presentation cryptographically.
  • Require the presentation server name to match the predicate target host.
  • Reject stale presentations outside the accepted freshness window.
  • Evaluate contains, regex, and jsonpath conditions deterministically over revealed data.
  • Reject unsafe regex conditions that risk catastrophic backtracking.
  • Reject proof payloads that reveal credentials such as Authorization, Cookie, X-API-Key, or Proxy-Authorization values.
  • Deduplicate accepted presentations to prevent replay.
